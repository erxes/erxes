# `accounting_ui` Plugin Guide

## Identity

- **Plugin:** `accounting`
- **Project:** `accounting_ui`
- **Layer:** `Frontend UI`
- **Path:** `frontend/plugins/accounting_ui`
- **Last synchronized:** `2026-11-11`

## Scope

### Owns

- Accounting routes, navigation, transaction list/detail/form experiences, accounting settings, journal reports, inventory/fixed asset accounting UI, and accounting-owned relation widgets.
- Fund and debt rate adjustment list, detail, form, calculation, transaction-run, subscription, and linked transaction display surfaces.
- Temporary account closing adjustment list, form, detail, calculation, row tax-percent edit, transaction-run, publish, and cancel surfaces.

### Does not own

- Backend accounting calculations, persistence, GraphQL schema definitions, or transaction journal handlers.
- Core product, branch, department, customer, company, organization settings, and shared UI implementations; consume them through public `ui-modules`, `erxes-ui`, and GraphQL APIs.
- Other plugin UIs, routes, state, or implementation details.

## Current Capabilities

- Fixed asset income keeps category/code/name acquisition entry in detail `followInfos.fixedAssetCategoryId`/`fixedAssetCode`/`fixedAssetName`; detail root keeps only the `fixedAssetId` reference, and income validation requires all three metadata fields. its row sheet edits frozen book/tax depreciation rules and optional custodian allocations. Settings fixed asset forms edit identity metadata only; financial values are derived API projections.
- Non-income asset rows and bulk-add actions use `settings/fixed-assets/components/chooser/FixedAssetChooser`. It has exactly two levels: assets and branch/department locations, with search/category/location/member filters, pagination and loading/error/empty states. The detail location supplies initial row-chooser filters; hidden transaction header locations are not used. Clicking an asset group adds its matching location choices, while leaf rows select one location. Custodians and serial allocations are managed through the transaction detail’s existing more-menu sheet, not as chooser rows or columns. Selected rows are excluded from available results and collect in a separate lower section; clicking them removes the pending choice. Selections survive filter/page changes. Branch and department have separate columns rendered by the public `BranchBadge`/`DepartmentBadge` in plain-text mode (id detail lookup), and asset labels stay compact on one line. Operational row choosers support multiple choices and insert one detail per choice; capitalization and revaluation keep one choice per asset. Choosing a location fills row branch/department and clamps quantity. Sale keeps its entered price and revenue account. Capitalization selects the asset across every location.

- The fixed asset add menu offers `Капиталжуулалт / Залруулга` (`fxaCapital`) for multiple assets per journal. `FxaChangeTable.tsx` and its rows load dated valuations, show prior unit cost/depreciation and quantity, capture new unit cost, total accumulated depreciation (including zero), with a derived editable unit helper, residual value, automatic method and new useful years, and preview only cost/depreciation entries in TBalance. There is no counterpart-account field or source `capitalAccountId`; accountants add ordinary transaction tabs to close the combined remaining difference. Useful years convert to the canonical annual rate. Existing acquisition master data remains unchanged.

- The fixed asset add-transaction menu includes `Дахин үнэлгээ` (`fxaRevaluation`), using `FxaChangeTable`/`FxaChangeRow` and the dated valuation preview shared with capitalization. `TransactionTabs` renders the table directly for both journals; no journal-specific wrapper components are needed. Both operate on all asset locations. Revaluation sheets show the prior loss/reserve limits and aggregate recovery, reserve usage, new loss and new reserve across that asset’s locations. Capitalization includes current-period corrections without valuation-limit allocation. There is no separate correction journal or subtype selector.

- The inventory Recalculate balances form distinguishes blank (all locations), `_` (“Салбар сонгогдоогүй” / “Нэгж сонгогдоогүй”), and real ids. Blank defaults leave selectors unselected. Clicking the selected unassigned-location option again clears that dimension; no separate all-location option is rendered. Sentinel labels never query `_` as a real structure id. Selected-product scoping is preserved.

- Inventory navigation includes `Ажлын гүйцэтгэл` at `/accounting/inventories/job-executions`, with searchable/status-filtered paginated records, multi-job create/edit/view sheets, independently scaled actual product/cost arrays, common date and inventory accounts/locations, confirmed post/undo/delete actions, and linked transaction navigation. No planned-quantity disclosure or duplicate plan state is rendered.

- Uses statically analyzable typed GraphQL documents with generated operation result and variable types; build, serve, and contract tests regenerate them automatically.
- Job master, item, cost and unwound-output response types derive from generated fragments/queries. Lists, details and selectors preserve nullable response fields; only `jobFormValues` converts them to editable form defaults, reused when selecting execution jobs. Do not restore response-wide `normalizeJob` adapters or handwritten Job response interfaces.
- Rspack awaits gateway schema composition and codegen before its first build or watch compilation, including remotes launched directly by the Module Federation host without Nx task dependencies.
- Displays, creates, updates, prints, and removes accounting transactions.
- Transaction rows on the receipts (`/accounting/main`) and journal entries (`/accounting/records`) lists open the detail with a `returnTo` query param holding the list URL and its filters (`buildTransactionEditPath`). `TransactionFormPage` renders an outline Back button (`IconArrowLeft`, `common` `navigation.back`) in the header end and points the header breadcrumb link, labelled `transactions` or `journal-entries` by its path, at that URL; deleting from the detail returns there too. The Add transaction menu on those lists opens the create form with the same `returnTo` (`buildTransactionCreatePath`), and saving a new voucher opens its edit page keeping that `returnTo` (`useTransactionsCreate`). `getTransactionReturnPath` maps the accounting home address (`/accounting`, which also renders the receipts list) to `/accounting/main` keeping its query, accepts only the two list paths, and falls back to `/accounting/main` for a missing or any other `returnTo`, so the link never leaves the lists.
- Transaction filters include account type, account status, account category (with its child categories), and off-balance account through the `accountKind`, `accountStatus`, `accountCategoryId`, and `accountIsOutBalance` query params. The same variables drive the list, record list, and export.
- The safe remainder list filters by one or more count statuses through the `statuses` query param.
- Transaction form save actions keep submit behavior unchanged but render `DRAFTED` status-group saves with the shared secondary button variant, warning-colored draft icon/text, and warning-colored debit/credit totals.
- Journal entry deletion (selection bar Delete and row more-menu Delete) goes through `useTrRecordsDelete`: it dedupes the selected lines by `parentId`, loads each parent with `accountingAccTransactionsDetail` (network-only), and confirms with the real scope — every transaction that shares the parent (a parent usually holds a pair entered together through the form's sub-tabs, such as bank + VAT, and removal deletes the whole pair), counted and listed one by one with its number, journal, date and line count; the total journal lines including unselected ones; and a warning when published transactions are included. Detail results whose `parentId` differs from the removed parent (related through `ptrId`/`originId`) are excluded, because removal by `parentId` keeps them — before sending one `accountingAccTransactionsRemove` per parent, one at a time so each list refetch lands after the previous removal. The selection-bar Delete uses `variant="secondary"` with `text-destructive`, and the confirm OK button uses the destructive variant. The selection is cleared only when every parent removal succeeds. Every delete control on the page shares the `trRecordsDeletingState` atom (`states/trRecordsDeletingStates.ts`): it is set while details load and while parents are removed, so a Delete from any control in that time is ignored and the selection-bar button is disabled. The atom is released before the confirm dialog opens, because the shared `useConfirm` promise never settles on Cancel; never hold the guard across `confirm`. Never call the remove mutation per selected row: one parent removes every line in it.
- Exports accounting main and journal record transaction lists through the platform import/export UI using the current frontend filters or selected rows.
- Transaction record rows place each detail amount in the debit or credit column using the transaction-level side; when that side is missing or not `dt`/`ct`, both columns render a `-` placeholder instead of `0` so missing data never reads as a zero balance. Journal entry cells in `TrRecordsTableColumns.tsx` take a typed `Row<ITrRecord>`, never `any`. `accTrRecordsMain` details carry no `product` object, so the product cell passes only `productIds` to `ProductsInline`.
- Transaction record tables initialize journal-specific columns before the table provider mounts so structural action and checkbox columns retain their fixed width.
- Keeps cash, bank, payable, and receivable transaction main-currency and foreign-currency amounts manually editable while syncing the paired amount from exchange rates without update cycles.
- Provides adjustment navigation and pages for inventory, fixed asset, fund rate, and debt rate adjustments.
- Provides closing adjustment navigation and pages for temporary account closing.
- Lists the check-sync rule pages (deal, POS order) in the `CheckSyncNavigation` navigation sub group, shown only on `/accounting/check-sync` routes, so the check-sync page carries no in-page sidebar.
- The check-sync POS order table shows the sync status translated through the `accounting` namespace status keys (`checked`, `synced`, `skipped`, `pending`, `error`, `resynced`).
- `AccountingSidebar` (`src/Sidebar.tsx`) renders the four module links (`MainNavigation`: receipts, journal entries, report, check sync) followed by the adjustment, inventory and fixed asset sections, each a `NavigationSection` row (icon, label, chevron) that unfolds its links with a grid-row transition and opens whenever the route enters its own section (path-segment match) and otherwise keeps the user's open or closed choice. Never use `NavigationMenuGroup` there — its muted, uppercase-styled group label reads as a disabled heading. Below them it renders the route-aware page menu `CheckSyncNavigation`. The receipts page (`/accounting/main`) has no page side menu: branch, department, and journal stay in `TransactionsFilter` with every other filter. The journal entries page (`/accounting/records`) renders `JournalNavigation` (`Sidebar.Panel` labelled `journal-entries`) as a second sidebar beside the header, and the `journal-entries` link in `MainNavigation` sets `sidebarPanelOpenState` to `true` so clicking it always opens that panel. `JournalNavigation` lists the transaction journals in a `journal` group, selected through the `journal` query param, sub-grouped and iconed from `TR_RECORD_JOURNAL_GROUPS`, which places every `TrJournalEnum` value, generated follow journals included, under its origin group (general, cash and bank, calculation, inventory, fixed asset); keep app-sidebar page menus route-gated so pages with their own side menu (journal reports) do not show an extra menu on every accounting page.
- Transaction activity opens in the app side panel, not a sheet: the transaction form's activity button (`TrRightSidebar` (`transactions/transaction-form/components/TrRightSidebar.tsx`), shown only once the voucher has a `parentId`) opens `accounting:transaction` through `useSettingsPanel(TRANSACTION_CONTENT_TYPE).openDetail` like every other accounting panel opener (`TRANSACTION_CONTENT_TYPE` in `transactions/constants/transactionPanel.ts`, keyed by `parentId`) and then switches to the `activity` tab through `useSidePanel().setTab` after the panel reports that record (no other accounting opener picks a tab). Unlike other accounting panels, whose Activity tab is the generic `SettingsPanelActivity` without a note input, the transaction Activity tab keeps the former sheet's custom rows and note input. `TRANSACTION_PANEL` (same file) has no draft view; its Detail tab shows the voucher number, date, status, description and the related deal/POS order link from `accountingAccTransactionsDetail` (`useTransactionsDetail`), and its Activity tab renders the transaction custom activity rows (created, status changed, approver changed) with `AddInternalNote`. `ISettingsPanelViews.New` is optional and `Activity` overrides the generic `SettingsPanelActivity`.
- Fund rate, debt rate, closing, inventory cost, fixed asset depreciation adjustments and safe remainder (inventory count) create/edit forms render in the app side panel instead of `AccountingSheet`; this is a UI-only move and their submit, navigation, validation and field logic match the former sheets. Content types: `accounting:adjustFundRate`, `accounting:adjustDebtRate`, `accounting:adjustClosing`, `accounting:adjustInventory`, `accounting:adjustFixedAsset` (`ADJUSTMENT_PANEL_CONTENT_TYPES` in `adjustments/constants/adjustmentPanel.ts`) and `accounting:safeRemainder` (`inventories/safeRemainders/constants/safeRemainderPanel.ts`). Add buttons render `SettingsPanelAddButton`; edit forms open from the table more-menu (closing) or the detail page Edit button (fund/debt rate) and close the panel after saving. Inventory cost, fixed asset adjustment and safe remainder are create-only, so their panel detail view renders nothing.
- Adjustment panel rows are shared through `adjustments/components/AdjustPanelFields.tsx` (`AdjustRateCurrencyFields`, `AdjustRateAccountFields`, `AdjustDateField`, `AdjustDescriptionField`), which take the form `control` as a prop. Never use `useFormContext` in this remote: erxes-ui `Form` provides the host's react-hook-form context, which the remote's own `react-hook-form` copy cannot read, so it returns `null` at runtime.
- Fixed asset category forms show both derived useful years and annual depreciation percentage; changing either field updates the other rounded to two decimals, while the backend stores the annual percentage as the canonical value.
- Uses system `dealCurrency` options for fund/debt adjustment main and foreign currency fields plus account currency selectors; rate adjustment main currency defaults from system `mainCurrency`.
- Fetches spot rate from the existing exchange-rate hook when adjustment date, main currency, and foreign currency are selected.
- Fund rate detail can calculate, show validation state, show account balances grouped by branch/department, run linked transactions, and display linked transaction rows.
- Debt rate detail can calculate, show validation state, show account/customer balances grouped by branch/department, run linked transactions, and display linked transaction ids.
- Fund and debt rate adjustment detail account balance grids, plus fund linked transaction rows, render with `RecordTable` instead of raw HTML tables.
- Closing adjustment list renders account fields inline, and detail can calculate temporary-account balances grouped by branch/department, show validation state, render read-only branch/department code-title labels plus account inline names, edit tax percentage per row in collapsible `RecordTable` groups, show generated transactions in a `TBalance`-style transactions tab, run closing transactions, publish, cancel, and show tax impact.
- Inventory transaction rows fill prices from product master, current inventory cost, or last completed inventory income price depending on journal behavior.
- Inventory out and internal movement rows show active unit cost and amount as read-only values; inventory sale unit price remains editable because it is the sale price, while its generated inventory and cost-of-goods rows retain the fetched active cost across sale quantity edits and are costed by the backend on save.
- Inventory income, out, move, sale, and sale-return bulk product additions fetch journal-specific fill data once, then append rows with the same price, cost, amount, and weight rules as single-row product selection.
- Inventory internal movement rows can toggle detailed view to edit source branch/department on the outgoing detail and destination branch/department on the generated incoming detail.
- Accounting sync settings include a deal movement rule page that captures the target sales stage, source/destination inventory accounts, default source/destination branch and department, and whether deal/product branch and department apply to the movement source or destination; the rule table's account, branch, and department cells are inline-editable and persist immediately through `useSyncConfigValueUpdate`, which queues each config's edits so overlapping cell changes are sent sequentially and merged onto the latest pending value instead of overwriting each other; deal movement check/resync uses its own `/accounting/check-sync/deal-movement` route and rule picker.
- The inventory cost adjustment journal has an independent form, supports single or bulk product selection, hides quantity input, shows current remainder and unit cost, accepts a per-unit cost delta, calculates the after-adjustment unit cost, and submits cost-only rows.
- Safe remainder counting opens one import sheet with separate TXT and CSV tabs, defaulting to CSV. CSV supports template download, field-format reference, drag-and-drop upload, sample values, editable column mapping with alias suggestions that ignore case, whitespace, underscores, and hyphens in headers (for example `Unit Price` maps to `unitPrice`), ignored columns, and required/duplicate mapping validation before import; TXT and CSV rows with blank total cost default counted total cost from active unit cost and counted quantity, while CSV accepts explicit `totalCost` and legacy `unitCost` aliases.
- Settings expose `Бараа материал` alongside Accounting and `Үндсэн хөрөнгө` as an independent entry at `/accounting/settings/inventories`, with its own `Ажил` sidebar item at `/accounting/settings/inventories/jobs`. Users can create, edit, list, and delete production-stage jobs with `Орц бараа` and `Гарц бараа`, units, quantities, output cost-allocation ratios, and duration.
- Safe remainder detail tables expose persistent user-controlled column order and subtly highlight editable counted quantity and total-cost inputs.
- Safe remainder quantity and counted total cost are the editable census values; derived debit/credit and adjustment amounts are read-only previews, and detail actions disable together while any census mutation is running.
- Inventory income can allocate additional expenses by amount, count, or editable total line weight; line weight initializes from core product weight multiplied by count.
- Inventory income and internal-movement income rows keep the source unit of measure in the table and expose infrequent product-splitting fields from a leading row action sheet; the sheet persists canonical `hasSplit` in that row's `followInfos.invSplit`, requires the resulting product and a positive ratio only when enabled, displays the result unit, highlights enabled row action buttons in yellow, and previews the generated `invOut` plus `invIncome` rows in `TBalance` before save.
- Fixed asset income, out, move, and sale transaction rows can toggle detailed view to edit branch and department per detail.
- Transaction balance rows display branch and department from each transaction detail when present, so generated follow rows with source/destination locations are shown at their row location instead of the root transaction location.
- Fixed asset income rows capture acquisition category, code, name, count, unit cost, tax settings, and optional detail-level branch/department values; code and name are editable inline table cells that participate in transaction-form keyboard navigation, and the backend creates the fixed asset from the saved detail.
- Fixed asset category draft and detail panels show both derived useful years and annual depreciation percentage (book and tax); the draft updates the paired field rounded to two decimals (`fixed-assets/utils/depreciationRate.ts`); both views render the book and tax groups from `FIXED_ASSET_CATEGORY_DEPRECIATION_FIELDS`, and the detail derives useful years from the stored rate and saves a useful-years edit as the converted annual percentage, because the backend stores the annual percentage as the canonical value.
- Fixed asset settings list income-created asset records without a direct add button; asset creation belongs to fixed asset income transactions.
- Fixed asset income detail sheets start with no owner-allocation rows by default; the owner-record add button shows the remaining quantity, lets users split the detail count into responsible-user/serial rows, and binds residual value plus `preDeprecation` only to each transaction detail's `followInfos`.
- Fixed asset out, move, and sale rows select existing fixed assets directly, while the "Олон хөрөнгө нэмэх" sheet can filter by category and append multiple selected assets as separate details; selected rows refetch fixed asset location remainder whenever fixed asset, branch, department, or date changes, can optionally select active owner records up to the detail count, out/move cost is based on asset data, sale keeps user-entered sale price, branch/department values stay on each detail, `fxaOut` only asks for accumulated depreciation account, and generated sale/depreciation follow previews use `fxaSaleOut`, `fxaDepOut`, and `fxaSaleCost`.
- Fixed asset out, move, and sale edit forms preserve persisted detail counts while location remainder loads; the remainder limits subsequent user edits but must not rewrite saved values during form initialization.
- Fixed asset disposal follow previews run only for unsaved transactions; persisted edit forms keep Mongo-backed main details and generated follow transactions until the backend recalculates them on save.
- Fixed asset navigation includes an "Үндсэн хөрөнгө" section with an owner-record list and a branch/department fixed asset remainder page; the redundant fixed asset settings and direct internal-move shortcuts are not shown there.
- The in-form add-transaction popover can create cash, bank, receivable, payable, or main transaction tabs directly from a selected account by resolving the account journal and pre-filling the first detail account; journal-only additions start with an empty account.
- Unknown addresses under `/accounting/*` render `AccountingNotFoundPage` (`src/pages/NotFoundPage.tsx`: accounting header plus `AccountingNotFound`, which shows the `common` `not-found` message and a Go back link to `/accounting/main`); unknown `/accounting/settings/*` addresses render `AccountingNotFound` linking back to `/accounting/settings/config`. There is no incomplete transactions screen (`accOddTransactions` is a deprecated backend placeholder), so the sidebar does not link `odd-transactions`; its `config.tsx` module entry is kept and opens the not-found page until that screen exists.
- `TR_JOURNAL_GROUPS` in `src/modules/transactions/types/constants.tsx` is the single source for origin (user-created) journals: `ORIGIN_TR_JOURNALS` derives from it, `AddTransaction` renders it, the transaction journal filter (`AccountsTrJournalCommand`) and the import guide (`TrImportGuide`) list it, and `hideInAdd` items (`tax`) are filterable but not creatable from the add menu. Generated follow journals stay out of those lists, while a link holding one still shows its label on the filter chip.
- The add-transaction popover (`AddTransaction`) stays anchored to the trigger end and renders a title, a `Command` search, and journal groups from `TR_JOURNAL_GROUPS` as CSS columns of icon-labelled groups (general, cash and bank, calculation, inventory, fixed asset): one column on small screens, two from `sm`, three from `md`, and a group never splits across columns. Its height is capped to the available viewport space and the list scrolls. Search values combine the group label, item label and journal so same-named items (`receipt`) stay distinct. Outside a form each item is a real `Link`, so modified clicks still open a new tab while Enter navigates through `onSelect`; inside a form an item calls `onClick`, and `SelectAccount` sits under the title. A disabled "Adjustment" item stays at the end, under the fixed asset group.
- Related account override inputs keep focus while users type and persist custom debit and credit code lists independently.
- Empty related account overrides are omitted on submit so backend-calculated default debit/credit related accounts remain active, and the related-account editor falls back to default `dt/ct` codes when `customDt/customCt` are empty.
- Accounting settings pages manage accounts, account categories, permissions, VAT, CTAX, and sync configuration; VAT/CTAX row access is guarded by the unified tax-row permission actions.
- `AccountSettingsBreadcrumb` keeps the shared `SettingsHeader` usable on narrow screens: below `sm` the root crumb shows only its icon and the current page crumb truncates instead of overflowing.
- `SettingsPage` wraps `MainSettingsForm` in its own `overflow-y-auto` container because the settings route layout clips with `overflow-hidden`; the form itself has no fixed height.
- The general settings form (`MainSettingsForm`) section grids collapse to one column below `sm`; full-width items use `sm:col-span-2` so they do not create an implicit second column on narrow screens.
- Account, account category, VAT row, city tax row, fixed asset category, fixed asset account set, inventory job card, and the four sync rules (`syncDeal`, `syncDealMovement`, `syncDealReturn`, `syncOrder`) open in the app side panel like core customers. Content types live in `constants/settingsPanel.ts` (`accounting:account`, `accounting:accountCategory`, `accounting:vatRow`, `accounting:ctaxRow`, `accounting:fixedAsset`, `accounting:fixedAssetCategory`, `accounting:fixedAssetAccountConfig`, `accounting:job`, `accounting:<syncCode>`); `config.tsx` registers every one from `SETTINGS_PANEL_CONTENT_TYPES` with `properties: false` and `draftTitle: true`, so core asks the plugin's `title` view for the draft header (`contentId` `new`) instead of its untranslated `New <type>` label. There are no settings Sheets, edit query params (`accountId`, `accountCategoryId`, `vat_row_id`, `ctax_row_id`, `configId`, `fixedAssetCategoryId`, `job_id`), or detail atoms.
- Each entity exposes one `ISettingsPanelViews` object (`ACCOUNT_PANEL`, `ACCOUNT_CATEGORY_PANEL`, `VAT_ROW_PANEL`, `CTAX_ROW_PANEL`, `FIXED_ASSET_PANEL`, `FIXED_ASSET_CATEGORY_PANEL`, `FIXED_ASSET_ACCOUNT_CONFIG_PANEL`, `SYNC_CONFIG_PANEL`) with `addLabel` (the translated draft header key: `add-account`, `add-account-category`, `add-vat`, `add-city-tax`, `add-fixed-asset`, `add-fixed-asset-category`, `add-account-configuration`, `add-configuration`, the same keys the old Sheets used), `editLabel` (the translated detail header key, also the old Sheet keys: `edit-account`, `edit-account-category`, `edit-vat-details`, `edit-city-tax-row`, `edit-fixed-asset`, `edit-fixed-asset-category`, `edit-account-configuration`, `edit-sync-settings`), `New`, `Detail`, and optional `Actions` and `Title`; `RecordPanel` renders the `title` view from `addLabel` (draft), the entity's `Title` (detail, when it has one) or `editLabel`. Account, account category, VAT, city tax and fixed asset category set `Title`: their name is edited in the panel's top bar through `SettingsPanelTitleField` and is not repeated in Detail. Other entities keep `editLabel`. `RecordPanel` otherwise only maps content types to these objects and draws activity with the shared `SettingsPanelActivity`. Add a new settings record type by adding a content type and a views object, not by branching in `RecordPanel`.
- Fixed asset settings rows and fixed asset custodian actions open in the app side panel. `FIXED_ASSET_CONTENT_TYPE` (`accounting:fixedAsset`) lives in `constants/settingsPanel.ts`, and the row more-menu Edit calls `openDetail`; there is no `fixedAssetId` query param or Sheet. `FxaOwnerRecordActions` and the owner table more-menu open `accounting:fxaOwnerReceive`, `accounting:fxaOwnerTransfer`, and `accounting:fxaOwnerHandOver` (`fixedAssets/ownerRecords/constants/ownerRecordPanel.ts`) through `useSidePanel().openNewRecord(contentType, defaults)`; `FxaOwnerRecordPanelNew` reads the row prefill with `useSidePanelDraft` and keys the form on it, so opening another row while the panel stays open shows that row. Submit data and the invalid-form toast match the old sheets, and `SettingsPanelDraftForm` takes `onInvalid` for the toast. The owner schema treats a defined `fromOwnerId` as a transfer and then requires `toOwnerId`, so only the transfer form may default `fromOwnerId` and `toOwnerId`; setting them in Create or Cancel blocks saving on a field those modes never render.
- `useSettingsPanel(contentType)` is the only way settings code opens panels: Add buttons (`AddAccount`, `AddAccountCategory`, `AddVats`, `AddCtaxs`, `AddFixedAssetCategory`, `AddFixedAssetAccountConfig`, `AddAccountingConfig`) render `SettingsPanelAddButton` (`openDraft`), table more-menu Edit and sync title/code cells call `openDetail(id)`, and drafts call `openDetail(newId, { replace: true })` after the create mutation, or `cancelDraft` on Cancel.
- Drafts save nothing until Save and use `SettingsPanelDraftForm` (`Form` + `PanelFormLayout`) with one `PanelFormRow` per field; text and number inputs and draft selects use `PANEL_INPUT_CLASS_NAME` (account category and fixed asset category drafts take their required name/code rows from `SettingsPanelNameCodeInputs`, which reads the draft form from context), category/currency use ghost chevronless triggers with `SETTINGS_PANEL_CELL_CLASS_NAME`, booleans use `SettingsPanelSwitch`, and plain-text descriptions use `SettingsPanelDescriptionInput`. Every text/number input and inline text field shows a placeholder: its `enter-*` key where one exists (account), otherwise its own label like the core customer draft (category, VAT, city tax). `TaxRowCommonFields` (draft) and `TaxRowCommonPanelFields` (detail) are shared by VAT and city tax rows.
- Account, category, VAT, city tax, fixed asset category, and fixed asset account set details edit inline: one `PanelField` per field built from `SettingsPanelFields` (`SettingsPanelCodeField` for the account category and fixed asset category code, `SettingsPanelTextField`, `SettingsPanelNumberField`, `SettingsPanelSelect`, `SettingsPanelSwitch`, `SettingsPanelDescriptionField` saved on blur, never `PanelDescriptionField`, whose BlockNote JSON would change stored plain text). Unchanged values never trigger a mutation; empty name/number/code values are ignored like the table cells. Account edits spread the whole account (backend requires code and category); while an account has no `categoryId` (e.g. migrated data), every field change except picking a category is skipped with a destructive `no-category-selected` toast instead of sending a mutation the backend rejects; category edits send `_id`, `name`, `code`, `parentId`, `description` plus the change and refetch `accountingAccountCategoryDetail` because the edit mutation returns only `_id`; VAT/city tax edits send only `_id` and the changed field and refresh the detail through the normalized cache; fixed asset category edits send every stored category field plus every change not yet reflected by the refetched record (`useSettingsPanelPendingChanges`, so overlapping inline saves never restore an earlier field's old value) (the backend requires `code` and `name`), clear the parent with `''`, and `useFixedAssetCategoryEdit` refetches `accountingFixedAssetCategoryDetail`; fixed asset account set details read the record from the `FIXEDASSET_ACCOUNTS` configs list by id, edit the asset account and the four related accounts with ghost `SelectAccount` triggers, and send the merged `value` (also through `useSettingsPanelPendingChanges`) with `subId` set to the asset account. Fixed asset category and account set inline edits toast errors only (`withMutationErrorToast`); their add and remove hooks keep success toasts. Delete actions use `SettingsPanelRemoveAction`, a header `⋮` `Popover` + `Command` menu shaped like the operation task actions menu, whose destructive Delete item closes the menu, confirms, then closes the panel; accounts gate it with `removeAccounts`.
- Sync rules keep their full forms in the panel instead of inline fields because pipeline/POS resets, `normalizeSyncConfigData`, and `subId` derivation depend on the whole form. `SyncConfigPanel` resolves the code from the content type, reads the rule from the `AccountingsConfigs` list by id, and mounts `SettingsRuleByCode[code].FormComponent` keyed by the rule id with `defaultValues` from its `value` (never `reset` after mount, which would trip `usePipelineReset`). Save merges into the stored `value` and keeps the panel open; Cancel closes it. Rule forms take `onCancel` and keep Save in both draft and detail. ## Data and State

- Income’s existing detail sheet accepts total detail prior unrecovered revaluation loss and prior reserve in `followInfos.revaluationLoss`/`revaluationReserve`. These are history limits, not additional cost deductions. Capitalization/revaluation depreciation previews use the existing `fxaDepIn`/`fxaDepOut` journal and origin types, linked by source `originId`. Revaluation persists only these same two signed total-detail delta fields; preview derives recovery/new loss/reserve from their signs. State sums them once without multiplying by quantity. Adjustment rows expose one current snapshot plus a read-only `previous` snapshot from generated query types. Asset/account and public branch/department inline cells identify each comparison row. Numeric snapshot cells show previous → current values; book values are derived from cost minus accumulated depreciation. No opening/closing or duplicate book-depreciation fields are stored or selected.

- Apollo Client owns server state, mutation refreshes, subscriptions, and detail/list cache updates.
- React Hook Form owns editable accounting transaction and adjustment form state.
- Inventory income detail form state stores total line weight; product or count changes recalculate it from core product weight, while direct weight edits persist until either source changes.
- Inventory split form state is detail-level `details[].followInfos.invSplit`; generated preview transactions live only in `followTrDocsState` and are excluded from submitted root transaction documents. Loading a legacy root `followInfos.invSplitDetails` entry migrates it into the matching detail form state.
- Inventory internal movement detail-level destination branch/department lives in `details[].followInfos.moveInBranchId` and `details[].followInfos.moveInDepartmentId`; generated `invMoveIn` details use those values and fall back to persisted generated detail locations or the root movement destination.
- Deal movement sync settings persist under the accounting config code `syncDealMovement`; each row uses the configured stage id as its config `subId`, and the check/resync page keeps a separate filter/table session from regular deal sync.
- Inventory cost adjustment detail state stores `count: 0`, `unitPrice` as the absolute per-unit cost delta, and `amount` as delta multiplied by current remainder; quantity is display-only, while editing after-unit cost derives the delta and increase/decrease side from its difference against current unit cost.
- Safe remainder import state and asynchronous file reads are owned by `inventories/safeRemainders/hooks/useSafeRemainderImport.ts`; TXT and CSV share `SafeRemainderImportUpload`. CSV views only render field reference/mapping; imported items derive from the current mapping rather than being copied into parent state. Reset, format changes, replacement uploads, and unmount invalidate earlier reads.
- Safe remainder blank counted cost defaults proportionally from active total cost; when quantity increases while active total is zero, the increased quantity uses `lastIncomePrice`. Explicit manual or CSV total cost, including zero, must bypass this fallback.
- Job form state is owned by React Hook Form and Zod; each card keeps separate `inputs` and `outputs` arrays, with output rows carrying raw cost-allocation ratios that default to one. Ratios have no percentage cap and must have a positive finite total; a row's allocation share is its ratio divided by that total.
- Job GraphQL documents share the `AccountingJobFields` fragment; selections must remain statically readable by the accounting GraphQL codegen pipeline.
- Job unit selection consumes core product `subUoms` and the `uoms` query through the composed gateway schema.
- Job duration selectors expose `real`, `minut`, `hour`, and `day`. `real` hides and clears duration; fixed units require a non-negative duration. Create defaults to `minut`.
- Job forms render separate `Хөдөлмөр` (`laborCosts`) and `Нэмэгдэл` (`overheadCosts`) editable tables. Each group supports any number of named amount/account rows, including none. Added rows require name, non-negative amount, and a write-permitted posting account; GraphQL uses only these arrays with no scalar cost/account fields or conversions.
- Each job cost table has a shared `Switch` that controls visibility only. Empty groups start collapsed; form reset/detail loading initializes each switch from that group's saved rows. Hiding preserves rows, removing the final row leaves the current switch state unchanged, and group validation errors reveal the table.
- Job edit forms initialize all row arrays to empty before asynchronous detail loading. Product-unit synchronization must tolerate unset/reset arrays and preserve already selected units when detail data arrives.
- Job forms batch selected input/output product `uom` and `subUoms` lookups through `AccountingJobProductUnits`. Selecting a different product clears the previous unit and defaults to its main unit when loaded; existing saved unit choices remain intact. Unit selectors offer the product's main and additional units, display master-unit names, and store unit codes.
- Safe remainder transaction labels and cost tabs must normalize adjustment differences from `-0.005` through `0.005` to zero, matching backend journal generation.
- Inventory row defaults initialize count to one; bulk-added rows also initialize all count-derived amount and weight values, batch journal-specific last-price, product, or current-cost lookup before append, and preserve sale/sale-return follow-journal unit cost by generated detail id.
- Jotai atoms under `src/modules/transactions/transaction-form/states` hold transaction form UI state, tax percentages, follow transactions, and rendering selections.
- URL query state owns selected detail ids and account table filters where existing accounting patterns use query params.
- `settings/account/components/filters/FilterHelpers.tsx` is the single source for account filter views and bar items. Reuse them on other pages through `queryKey`, `filterKey`, and `labelKey`; `AccountsFilterTrStatus` and `FilterBarTrStatus` also take `statuses` and `labels` so other documents reuse the same multi-select.
- Filter helpers read the cursor key from the surrounding `Filter sessionKey`, so a filter change resets the table cursor. Transaction filters pass `ACCTRANSACTIONS_CURSOR_SESSION_KEY`, the key `useTransactionsVariables` reads on both the main and record lists.
- Inventory, fixed asset, fund rate, and debt rate adjustment detail hooks subscribe by the selected `adjustId`, resubscribe when it changes, and replace the loaded detail with the published payload; empty events keep the previous detail. Inventory, fixed asset, fund rate, and debt rate detail queries and the inventory details-list query use `cache-and-network`, so reopening a detail page revalidates a `running` status left in cache by a run that finished while the page was closed.
- `useAdjustFxaDetails` loads the depreciation rows with `cache-and-network` and listens to `accountingAdjustFixedAssetChanged` through its own `useSubscription` (not `subscribeToMore`), so a failed reload never detaches it. Every non-empty event whose status is not `running` reloads page 1 with `no-cache` and `queryDeduplication: false`, and only the latest reload is written back with `writeQuery`; `handleFetchMore` does nothing while a reload is pending, and a page that started before a reload is discarded. A failed reload shows a destructive toast with the error message.
- Creating an inventory adjustment navigates to its existing `/accounting/adjustment/inventory/detail?id=` route; there is no `/edit` route.
- Inventory adjustment runs finish in the background; `useAdjustInventoryRunFinished` refetches the details list when a loaded adjustment leaves `running` or receives a new `checkedAt` while not running, so a missed `running` event still refreshes it; first load, publish/cancel and switching adjustments do not refetch. A failed post-run refetch shows a destructive toast with the error message. The run mutation selects only `_id` and has no `refetchQueries`, so a late mutation/refetch response can never overwrite the subscription's newer status or race the post-run details refetch.
- Closing detail state is owned by Apollo queries/refetches; percent edits and calculate/run mutations refetch detail state immediately.
