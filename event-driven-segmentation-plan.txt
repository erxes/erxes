EVENT-DRIVEN MATERIALIZED SEGMENTATION — ЭЦСИЙН ТӨЛӨВЛӨГӨӨ

Үндсэн шийдэл
==============

Segment-ийг ашиглах бүрдээ MongoDB/Elasticsearch дээр хүнд query ажиллуулахгүй.
Data болон time event бүрийн дараа нөлөөлөх segment-үүдийг reevaluate хийгээд,
тухайн record-ийн segmentIds-ийг materialize хийнэ.

Дараагийн feature-үүд:

  Customers.find({ segmentIds: segmentId });
  Deals.find({ segmentIds: segmentId });

гэдэг тогтмол, indexed query ашиглана.

6. RECORD ДЭЭР MEMBERSHIP ХАДГАЛАХ
==================================

Customer/deal зэрэг segment-ийн subject болж болох schema бүрд:

  segmentIds: {
    type: [String],
    default: [],
  }

Index:

  schema.index({ segmentIds: 1, _id: 1 });

Хэрэв tenant нэг collection дотор тусдаа талбартай бол:

  { subdomain: 1, segmentIds: 1, _id: 1 }

Нэмэх:

  await Model.updateOne(
    { _id: subjectId, segmentIds: { $ne: segmentId } },
    { $addToSet: { segmentIds: segmentId } },
  );

Хасах:

  await Model.updateOne(
    { _id: subjectId, segmentIds: segmentId },
    { $pull: { segmentIds: segmentId } },
  );

$push ашиглахгүй. Duplicate event-ээс хамгаалахын тулд $addToSet ашиглана.

segmentIds array нь зөвхөн:

- executionMode: materialized;
- status: active;
- automation/campaign/shared operational хэрэглээтэй

segment-үүдийг хадгална. Бүх private saved filter-ийг автоматаар materialize
хийж болохгүй.

8.1 Reliability анхааруулга
---------------------------

Одоогийн auto-capture:

- update/delete-ийг барьдаг;
- create бүх schema дээр баригдахгүй;
- best-effort queue publish хийдэг;
- failure нь original write-ийг унагадаггүй.

Тиймээс production segmentation-ийн message алдахгүй баталгаанд одоогийн audit
capture дангаараа хангалтгүй.

Сонголт A — MVP:

- Одоогийн put_log event ашиглана.
- Хурдан хэрэгжинэ.
- Local benchmark хийхэд хангалттай.
- Message loss боломжтой.
- Production exact membership баталгаа өгөхгүй.

Сонголт B — production:

- Plugin mutation болон durable outbox-ийг нэг Mongo transaction-д бичнэ.
- Entity update + segmentation_outbox insert.
- Logs service outbox-ийг publish хийнэ.

Standalone Mongo transaction дэмжихгүй бол schema hook event + durable journal +
reconciliation хослуулж eventual repair хийнэ.

12.1 Plugin дуудлага
--------------------

Independent evaluator-уудыг parallel дуудна.

  const results = await Promise.allSettled(
    evaluatorGroups.map((group) =>
      sendTRPCMessage({
        pluginName: group.pluginName,
        module: 'segments',
        action: 'evaluateBatch',
        input: group.input,
      }),
    ),
  );

Result:

  type SegmentEvaluationState =
    | 'matched'
    | 'notMatched'
    | 'unknown';

AND:

- Аль нэг notMatched -> notMatched.
- Бүгд matched -> matched.
- Бусад -> unknown.

OR:

- Аль нэг matched -> matched.
- Бүгд notMatched -> notMatched.
- Бусад -> unknown.

unknown үед membership өөрчлөхгүй. Retry хийнэ. Plugin timeout бол notMatched
гэж үзэж болохгүй.


13. MEMBERSHIP UPDATE RELIABILITY
=================================

Зөвхөн $addToSet/$pull хийгээд дараа нь count өөрчлөхөд distributed failure
үүснэ:

  record update амжилттай
    -> response-оос өмнө timeout
    -> retry дээр modifiedCount = 0
    -> counter update алдагдана

Тиймээс plugin membership apply нь transition event/outbox үүсгэнэ.

Subject plugin-ийн DB дотор:

  record.segmentIds update
  + segment_membership_outbox insert

боломжтой бол transaction-д хийнэ.

  interface ISegmentMembershipTransition {
    transitionId: string;
    segmentId: string;
    revision: number;
    subjectType: string;
    subjectId: string;
    from: boolean;
    to: boolean;
    evaluationVersion: string;
    createdAt: Date;
    publishedAt?: Date;

Unique index:

  { transitionId: 1 }

эсвэл:

  {
    segmentId: 1,
    revision: 1,
    subjectId: 1,
    evaluationVersion: 1
  }

Core stat consumer transition-ийг idempotent боловсруулна:

- false -> true: count +1.
- true -> false: count -1.
- бусад: no-op.


14. CATCH-UP BUILD
==================

Segment create/update хийхэд realtime mode руу шууд орохгүй.

  draft -> building -> catchingUp -> ready/active

Шинэ collection:

  segment_builds

  interface ISegmentBuild {
    segmentId: string;
    revision: number;
    subjectType: string;

    status:
      | 'pending'
      | 'scanning'
      | 'replaying'
      | 'ready'
      | 'failed';

    cursor?: string;
    watermark: number;
    processedCount: number;
    matchedCount: number;
    retryCount: number;
    error?: string;
    startedAt: Date;
    updatedAt: Date;
    completedAt?: Date;
  }

Алгоритм:

1. Segment revision 2 compile.
2. Current event watermark W авна.
3. Subject plugin listSubjectIds(cursor, 1000) дуудна.
4. evaluateBatch ажиллуулна.
5. Revision 2 membership-үүдийг build namespace-д бичнэ.
6. Cursor checkpoint хадгална.
7. Дараагийн batch руу орно.
8. Base scan дуусна.
9. W-с хойших event-үүд replay хийнэ.
10. Revision 2 ready болно.
11. activeRevision = 2 болгоно.
12. Revision 1 membership-ийг background cleanup хийнэ.

Build үеийн membership-ийг шууд active segmentIds array-д холихгүй.

Сонголт 1 — revision key:

  segmentMembershipKeys: ['segment-1:revision-2']

Activation дараа query active revision key ашиглана.

Сонголт 2 — shadow collection:

  segment_membership_builds

дотор хадгалаад ready болоход subject records руу bulk apply хийнэ.

Эхний implementation-д revision key ашиглах нь энгийн.

17. SEGMENT QUERY CONTRACT
==========================

Одоогийн fetchSegment-ийг эхний өдөр шууд устгахгүй.

Шинэ API:

  segmentMembers({
    segmentId,
    cursor,
    limit,
  });

Core segment-аас:

- contentType.
- activeRevision.
- status.

авна. Дараа нь subject plugin руу:

  listBySegment({
    segmentId,
    cursor,
    limit,
  });

Subject plugin query:

  Model.find({
    segmentIds: segmentId,
    _id: { $gt: cursor },
  })
    .sort({ _id: 1 })
    .limit(limit + 1);

Count:

  segmentStat({ segmentId });

segment_stats.memberCount буцаана.

Compatibility:

- dynamic segment -> хуучин fetchSegment.
- materialized + ready -> segmentIds.

20. RETRY, ORDERING, REPLAY
===========================

Queue settings:

- Exponential backoff.
- Finite retries.
- Failed job хадгалах.
- DLQ.
- Explicit replay command.
- Queue concurrency env-аар тохируулах.
- Tenant fairness.

Ordering:

Event дээр entityVersion эсвэл monotonically increasing sequence ашиглана.

  if (incomingVersion <= processedVersion) {
    return;
  }

Coalescing:

Нэг subject дээр богино хугацаанд олон event ирвэл:

  segmentId + subjectId

job key ашиглаж collapse/debounce хийнэ. Evaluation current state шалгадаг тул
хамгийн сүүлийн нэг evaluation хангалттай.

Unknown:

  plugin timeout -> unknown
  unknown -> membership unchanged
  unknown -> retry
  retry exhausted -> DLQ + segment health warning


21. RECONCILIATION
==================

Realtime system байсан ч repair path заавал байна.

  segment-reconciliation worker

Дэмжих ажиллагаа:

- Rebuild whole segment.
- Recheck one subject.
- Recheck cursor range.
- Recount membership.
- Replay event range.
- Repair counter.

Schedule:

- Critical active segment -> periodic sample.
- Count mismatch -> full recount background.
- DLQ recovery -> targeted reevaluation.
- Admin manual rebuild.
